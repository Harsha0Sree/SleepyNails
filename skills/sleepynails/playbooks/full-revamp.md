### Full Revamp

**You own the upgrade ceiling and the frozen contract. Everything internal may be redesigned to today's frontier standard. Nothing user-facing may break or drift.**

This is the default playbook when the operator invokes `/sleepynails` on an existing codebase built by an older model.

1. Establish git safety and baseline metrics first. Verify working tree status, create a dedicated upgrade branch (`sleepynails/revamp-<date>`) unless already on one, and run `scripts/baseline-snapshot.sh .sleepynails/baseline before`. Record build time, test results, and bundle or binary size where applicable.
2. Open the decision trail via **upgrade-trail** (`upgrade-decisions.tsv`) and log the baseline checkpoint.
3. Freeze the behavioral contract via **contract-pin** (**principle-pin-before-you-touch**, **principle-zero-behavioral-drift**). Inventory every route, API endpoint, request/response schema, persisted storage key or DB table, CLI command/flag, env var, and core user journey. Write runnable characterization tests or smoke harnesses for any uncovered critical path and prove they pass on the current codebase before changing production code.
4. Run **ceiling-audit** across the repository. Catalog concrete older-model compromises across six dimensions (Architecture & State, Type Safety & Boundaries, Performance & Data Flow, Security & Resilience, UI/UX Craft & Accessibility, Code Clarity & Dead Weight). Rank findings by impact. Do not waste effort polishing code that is already crisp.
5. Design the target architecture via **upgrade-architect** (**principle-upgrade-from-first-principles**, **principle-model-the-domain**). Ask what today's frontier model would build from day one knowing every pinned production invariant. Sketch two competing shapes for any cross-file core and commit to the simpler single-owner shape.
6. Execute Wave 1 (Subtraction). Apply **principle-subtract-before-you-upgrade**. Delete dead files, unused dependencies, stale compatibility wrappers, duplicated helpers, and dead feature branches. Re-run the contract pin and commit the subtraction slice cleanly.
7. Execute Wave 2 (Domain & Type Core). Apply **principle-type-system-discipline**, **principle-boundary-discipline**, and **principle-outcome-oriented-upgrade**. Replace `any`, unsafe casts, stringly-typed flags, and scattered conditionals with explicit domain types, boundary parsers, and pure core functions. Migrate all callers in the same wave and delete legacy internal APIs immediately. Verify the contract pin stays green.
8. Execute Wave 3 (Runtime, Performance & Hardening). Eliminate N+1 queries, redundant re-renders, blocking startup paths, silent catch blocks, and race conditions identified in the ceiling audit. Measure each win against the before baseline (**principle-prove-equivalence-and-gain**).
9. Execute Wave 4 (UI/UX & Surface Craft). If the project has a UI or CLI surface, apply **principle-experience-first-polish**. Upgrade layout hierarchy, typography, spacing, responsiveness, keyboard/screen-reader accessibility, and empty/loading/error states while preserving every existing feature, route, and user flow.
10. Execute Wave 5 (Unslop & Structural Guards). Run **unslop-code** to remove older-model comment noise, defensive clutter, and leftover tells. Encode the highest-value fragilities discovered during the run as lint rules, type constraints, or regression tests (**principle-encode-lessons-in-structure**).
11. Run final verification. Capture post-upgrade metrics with `scripts/baseline-snapshot.sh .sleepynails/baseline after` and compare via `scripts/verify-equivalence.sh`. Run **upgrade-blast-radius** on all public/persisted boundaries and **upgrade-interrogate** to try to break the upgraded build. Fix every proven failure and re-verify.
12. Organize commits into small verifiable units (**principle-sequence-verifiable-waves**), audit `upgrade-decisions.tsv`, and hand back the upgrade report.

**Reply:** frozen product scope, playbook used, before-vs-after metric table (measured), concrete upgrades landed per wave, contract equivalence proof, any pre-existing bugs discovered (kept separate), and the decision trail path.
